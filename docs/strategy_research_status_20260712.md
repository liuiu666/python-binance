# BTC 10分钟二元期权策略研究状态

更新时间：2026-07-12

## 目的和边界

本文件保存当前策略、回测和数据采集的真实状态，避免把旧脚本结果、不同执行口径和线上实盘表现混为同一个结论。

- 二元期权按 10 分钟到期、5U 单笔、80% 赔付口径评估。
- 回测必须使用信号发生时已经可见的数据；入场、冷却、到期结算和线上核心逻辑一致。
- 参数不能为了当天胜率调优。历史数据只用于提出假设，未参与调参的后续日期用于盲测。
- `auto_btc.js` 不属于本轮策略和数据采集改造范围。

## 当前线上策略

当前配置文件 `data/prod_config.json` 有两个启用且允许实盘的策略。

### 1. `BTC_10min_NORMAL_LIQ_OB_V2_QUALITY`

- 线上模型：`second_normal_trend_orderbook_latch_v2`
- 逻辑：在 600 秒正态震荡已确认时，等待价格越过边界后回到区间内，再由订单薄和主动成交确认反转方向。
- 核心风险控制：数据覆盖、中心斜率、sigma 范围与扩张、订单薄时效、同策略 600 秒间隔。
- 附加处理：假买墙陷阱、下跌做空时买盘快速消失、做多时主动成交仍为负、趋势空间过滤。

重要说明：这个线上 V2 不是早期 `second_normal_liquidity_orderbook_v1`。旧研究脚本若没有调用 `NormalTrendLatchEngine`，不能拿来证明当前线上版本的胜率。

### 2. `BTC_10min_MULTI_NORMAL_HF_STABLE_V1`

- 线上模型：`second_multi_normal_hf_stable_v1`
- 逻辑分两支：低波动正态区间的回归，以及成熟趋势末段的衰竭反转。
- 窗口：600 秒正态窗口，600 秒到期，同策略 600 秒间隔。
- 两个方向均可交易；不是“只做空”。

## 已确认的市场认识

交易核心不是价格会服从固定正态分布，而是拍卖过程中的接受、拒绝、流动性和订单流。

1. **平衡回归**：价格大部分时间围绕价值中心交易；边界假突破后回到价值区，才可能有回归机会。
2. **趋势行走**：价格沿正态带边界持续运行时，边界不是反转信号，逆势均值回归风险很高。
3. **价值区迁移**：突破后若价格能在旧价值区外停留，且主动流和流动性同向，旧正态区间已经失效。
4. **假突破/假支撑**：下跌中突然堆积买盘但价格继续走弱，可能是买墙被吃掉或假支撑，不应机械做多。
5. **转换期**：波动扩张、中心斜率变化、订单薄快速撤单但方向尚未确认时，最容易出现回测好、实盘差的问题，应降低交易意愿而不是强行寻找单子。

## 当前问题

1. 回测高、实盘低的风险仍未完全解决。首要检查顺序是：数据时间、信号时间、锁存/冷却、执行价格、结算价格，以及线上和回测是否调用同一核心。
2. 早期研究存在多种脚本和参数版本，已知不能再把它们拼成一个“总胜率”。
3. 新订单薄原始数据从 2026-07-12 才开始积累，尚不足以支持高频拍卖策略的长期结论。
4. 当前 `signal_btc.py` 每秒重载并计算较长秒级窗口；性能优化必须保证信号逻辑不变。

## 2026-07-12 低波动回归修复

今天真实交易拆分显示，成熟趋势衰竭分支仍为正收益，主要亏损来自低波动正态回归。原实现虽然文案写“成交流转向”，实际只检查过去5分钟平均成交流，没有确认最后30秒是否仍向正态区间外推进。

共享核心现增加因果短周期保护：低波动尾部信号除了原有条件，还要求预测方向上的最近30秒收益不低于 `-0.5 * sigma10_bps`。也就是最近30秒继续向区间外移动超过当前10分钟波动的半倍时，不做机械回归；趋势衰竭分支不受影响。

2秒执行延迟回放：

| 数据 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 历史三段 | 76单 / 72.37% / +115U / 回撤21U | 69单 / 72.46% / +105U / 回撤15U |
| 7月12日独立段 | 17单 / 41.18% / -22U / 回撤25U | 7单 / 57.14% / +1U / 回撤6U |
| 原四段合计 | 88单 / 71.59% / +127U / 回撤21U | 78单 / 70.51% / +105U / 回撤15U |

参数比例在 `0.25` 至 `0.5` 区间、执行延迟在2秒至5秒时结论稳定。把被保护规则挡掉的信号直接反向追突破，在今天为10单/70%，但历史反向分支只有9单/44.44%，因此已否决，没有上线。后续高频增量必须等待近价位深度增减数据积累后，验证吸收与流动性真空，不使用旧全深度订单薄拟合补单。

## 2026-07-12 2分钟聚合研究

重新按因果时间对齐2分钟K线：信号秒恰好结束一根2分钟K线时，允许使用这根刚完成的K线，不额外退后一根。历史、独立段和今天没有重叠使用。

验证了三种组合方式：

1. **恢复被30秒保护挡掉的回归信号**：严格要求完整2分钟K线已经向回归方向转动。历史段没有触发；独立段2单全胜；今天4单/50%/-2U。样本结构不一致，不上线。
2. **2分钟独立产生方向**：平衡尾部做回归，接受迁移做顺势。今天23单/69.57%/+29U，但历史140单/40.71%/-187U，属于明显近期行情拟合，不上线。
3. **2分钟只给现有信号投票**：历史中，2分钟顺势方向与成熟趋势衰竭信号冲突时，现有反向衰竭信号为27单/81.48%/+63U；今天同类为4单/50%/-2U。2分钟冲突本身不能作为固定否决或反向依据。

当前结论：2分钟聚合适合作为行情标签和趋势年龄观察层，但尚不能稳定提高方向胜率。下一步需要把2分钟趋势冲突与近价位订单增减、主动成交后的价格进展联合起来，区分“流动性真空下继续走”与“吸收后衰竭”，而不是继续调2分钟价格阈值。

## 2026-07-12 性能记录

服务器内存异常的主因不是秒 K、订单薄或新拍卖采集器，而是信号服务启动时的审计去重读取：

- `data/signal_audit.jsonl` 已增长到约 652MB、21.8 万行；
- 原实现使用 `readlines()` 读取整个文件后才截取最后 2 万行；
- 这会让 `signal_btc.py` 在启动时占用约 1.25GB 匿名内存，应用服务整体约 1.4GB。

已部署的修复：`py/signal_state.py` 改为从文件尾部读取所需 JSONL 行，不再全量加载。策略参数、信号判断、下单脚本和历史审计内容均未改动。

修复后观测：

- 信号进程约 433MB；
- 应用服务整体约 741MB；
- 系统可用内存约 1.5GB；
- 秒 K、订单薄和拍卖采集健康检查均正常。

此外，秒级缓存已改为在文件增长时只读取并合并最近片段，而不每秒重新解析完整滚动窗口。后续仍应将 `signal_audit.jsonl` 按天归档，避免日志文件继续无界增长。

## 新数据采集状态

新服务：`btc-auction-data.service`，独立于秒 K、旧订单薄和策略服务。

按 UTC 日期保存：

```text
data/auction/BTCUSDT/futures/trades/date=YYYY-MM-DD/events.jsonl.gz
data/auction/BTCUSDT/futures/depth_updates/date=YYYY-MM-DD/events.jsonl.gz
data/auction/BTCUSDT/futures/force_orders/date=YYYY-MM-DD/events.jsonl.gz
```

采集内容：

- 逐笔成交及主动买/主动卖方向；
- 100ms 订单薄增量、买卖盘新增与撤除、前 20 档深度、价差和失衡；
- 爆仓事件；
- 订单薄序列断档和重同步次数；
- 健康状态：`GET /api/auction-data-health`。

原始深度数据采用按秒关闭的 gzip 分段，已验证可实时读取；异常中断最多影响最后一个未完成秒分段。2026-07-12 上线后的状态为订单薄已同步、断档 0、端到端事件年龄约亚秒级。

本地特征汇总器：`py/build_auction_features.py`。它只把原始事件转换为因果的每秒特征，不生成交易信号：

- 10/30/60 秒主动买卖流及失衡；
- 买卖盘新增、撤除和净流动性压力；
- 深度、价差、订单薄失衡和覆盖率；
- 爆仓方向与数量；
- 10/30/60 秒价格变化。

## 接下来的研究方法

不等待 7 天才开始，但也不在几小时数据上宣布策略成立。

1. 立即：用已有秒 K 和旧订单薄数据提出固定的拍卖假设，不改新原始数据的阈值来追求当天胜率。
2. 6 至 12 小时：检查新原始数据的覆盖、断档、事件顺序和特征分布，确认数据质量。
3. 24 小时：将当天未参与调参的数据作为第一段盲测，验证假设方向是否存在。
4. 多日期：按平衡回归、失败拍卖、价值区迁移、转换期不交易四类状态分别统计单数、胜率、收益、最大回撤和最大连亏。
5. 只有同一核心在回测、影子和实盘三处一致，且跨日期仍成立，才允许调整实盘策略。
